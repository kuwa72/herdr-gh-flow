## 1. エグゼクティブサマリ（結論：So What）

1. **競合ツールの空白地帯（The Gap）**:
   - 既存の GitHub CLI 拡張（`gh-dash`, `gh-i`, `gh-sherpa` 等）は「閲覧・ステータス確認」や「単一操作の自動化」で完結しており、AIエージェントへのコンテキスト引渡しやTDD強制力を持たない。
   - 一方、自律/対話型AI CLI（Claude Code, Aider, Devin）は「端末内での対話・コーディング」に特化しており、Issue選定、ブランチ管理、TDDテスト失敗確認（Red）、PR作成、非同期CI追従〜Auto-mergeまでの**開発サイクル全体（Outer Loop）を統制する仕組みがない**。
2. **`hgf` のコアバリュー（Core Value）**:
   - `herdr-gh-flow` (`hgf`) は、**「GitHub Issue」を起点に「TDDガードレール付きプロンプト動的注入」→「Herdrマルチペインによる人間見守り・即時介入」→「堅牢なCI待機（ci-wait）〜Auto-merge」までを一気通貫で接着するオーケストレーター（Glue）**である。
3. **親課題 #16 への具体的提言**:
   - **提供形態**: **「ハイブリッド型（単体CLI優先 + Herdr環境自動検知 + gh extension互換）」** を推奨。
     - 単体CLI `hgf`（またはバイナリ）をコアとし、Herdr環境（`HERDR_ENV=1`）下では自動でペイン分割・ライフサイクル連携を発動、Herdr外ではインラインフォールバックする。
     - かつ `gh hgf` / `gh flow` としてインストール可能な構成にしておくことで、gh エコシステムの導入容易性を最大活用する。
   - **UX設計**:
     - Issue一覧では `fzf`（プレビュー付き）を使い、エージェント選択ステップを挟まずにキーバインド（`Enter`: agy, `Ctrl-D`: devin, `Ctrl-O`: opencode）で**1アクション起動**させる。
     - ペイン分割後はプロンプトを「事前入力状態（コマンドライン展開）」にしてフォーカスを当て、開発者が `[Enter]` で開始できる**Human-in-the-loop（介入・レビューファースト）**を基本とする。

## 2. 開発者の日常ワークフローにおける摩擦（フリクション）の解剖

Issue着手から完了に至る標準的な開発サイクルにおいて、各ツールでどこに手動のオーバーヘッドが発生しているかを整理する。

```
[Issue確認] ──> [ブランチ作成] ──> [TDD/プロンプト投入] ──> [実装・テスト実行] ──> [PR作成] ──> [CI待機・マージ]
```

| ステップ | 一般的な開発者の操作フリクション | 既存ツールの限界 | `hgf` による解決 |
| :--- | :--- | :--- | :--- |
| **1. Issue確認** | ブラウザまたは `gh issue list` で探す。番号や仕様を手動コピーする。 | `gh-dash`, `gh-i`: 閲覧は快適だが「次の作業」に繋がらない。Claude Code等: 手動でIssue URLや指示文を入力。 | `gh issue list` + `fzf` プレビューで内容を即確認。1キーで作業ブランチとプロンプトへ直結。 |
| **2. ブランチ作成** | `git checkout -b issue/XX-title` を手打ち。命名ブレが発生。 | `gh-sherpa`: ブランチは作れるがエージェント起動は別。 | Issueタイトルから自動スラッグ化し `issue/<no>-<slug>` を即時チェックアウト。 |
| **3. TDDプロンプト注入** | 「テストを先に書け」「失敗を確認しろ」という指示を毎回プロンプトに手動記述。 | エージェント単体: 規約を忘れて実装から着手しがち（Green検証なしでコード生成）。 | Issue本文＋受け入れ条件＋TDD厳格ルール（Red→Green→run-tests）を動的に合成して注入。 |
| **4. 実装・見守り・介入** | 単一ターミナルだとエージェントの出力で画面が埋まり、Git diffや別作業ができない。 | Claude Code / Aider: 端末専有。Devin: Webで完結するがローカル環境とのギャップ大。 | Herdrで右ペインに分割起動。左ペインでローカルGit・テストログを監視しながら即介入可能。 |
| **5. PR作成** | `gh pr create` を打ち、コミットログやIssueリンクを手動整形。 | ユーザー任せ、またはエージェントが不揃いなフォーマットでPRを作成。 | プロンプト規約により `gh pr create --fill` を義務付け、Issue自動紐付け。 |
| **6. CI待機〜Auto-merge** | GitHub Actionsの実行開始待ち（15秒〜30秒の未登録ラグ）、完了をブラウザリロードや連打で監視。 | `gh pr checks --watch`: PR直後のラグで「no checks reported」終了する。コンフリクト非同期判定に弱い。 | **`ci-wait`**: チェック未登録・再生成・コンフリクト判定を吸収し、通過後に安全にsquash merge。 |

## 4. カテゴリ別エコシステムの詳細分析

### 4.1 Herdr エコシステムとの親和性と限界
- **現状の役割**:
  - `herdr integration install claude/devin/antigravity-cli` 等により、各エージェントのシェルラッパー、セッション状態検知（`idle`, `working`, `blocked`, `done`）、通知フックが提供されている。
  - `herdr pane split` / `herdr pane send-text` / `herdr worktree` などの低レイヤAPIが整備されている。
- **限界**:
  - Herdrはターミナルマルチプレクサ＋エージェントライフサイクル基盤であり、「GitHub Issueをどう読み解き、どういうTDDプロセスでPR作成まで導くか」という**開発ワークフローの責務（ドメインロジック）は持っていない**。
- **hgfとの親和性**:
  - `hgf` はHerdrの上に乗る「オーケストレーション・レイヤー」として最適。Herdrに欠けている「GitHubタスクのコンテキスト管理」を埋める存在となる。

### 4.2 GitHub CLI (`gh`) エコシステムとの比較
- **gh extension の特性**:
  - `gh extension install <repo>` で即導入可能。Go製シングルバイナリまたはシェルスクリプトで配布される。
  - `gh-dash`（TUIダッシュボード）や `gh-poi`（ブランチ整理）のように、UNIX哲学に基づき単一の課題を鋭く解決するツールが多い。
- **`hgf` を gh extension（`gh hgf` / `gh flow`）にするメリット・デメリット**:
  - **メリット**:
    - `gh` コマンドライン体系に自然に溶け込み、GitHub認証（`gh auth`）を前提にできるため認証設定が不要。
    - GitHubを利用するエンジニアへのリーチ（配布・アップデート）が容易。
  - **デメリット**:
    - Herdr（ローカルマルチプレクサ）という「GitHub外のシステム」に依存する部分があるため、純粋なGitHubツールと捉えると環境依存が生じる。
  - **解決策**:
    - Herdr外でも単体CLIとしてインライン起動できるグレースフル・デグラデーション（Graceful Degradation）を徹底することで、gh extension としても自然に成立する。

### 4.3 AIエージェント駆動CLIとの住み分け
- **対話型（Claude Code, Aider, OpenCode, Antigravity CLI）**:
  - 得意領域: ファイル編集、Git変更の把握、対話的な問題解決。
  - 弱点: タスク着手時のコンテキスト注入（どのIssueか、どんなブランチ名か、TDDを遵守させるか）を人間が指示し続けなければならない。
- **自律型（Devin, SWE-benchフレームワーク）**:
  - 得意領域: プロンプト投入後の完全自律PR作成。
  - 弱点: 途中の思考プロセスへの介入が難しく、ローカルDBや特殊なローカル環境テストの再現が困難。
- **`hgf` の立ち位置**:
  - エージェントと競合するのではなく、エージェントを**「ワーカー（Worker）」として統制・召喚する「ディスパッチャー（Dispatcher）」**。

## 5. 親課題 #16（提供形態・UX設計）への論理的な提言

### 提言1: 提供形態は「ハイブリッド（単体CLI + Herdr自動検知 + gh ext互換）」を採用すべき
1. **コア実行体**: `bin/hgf` を単一のエントリポイントとする（将来的にGo言語等でバイナリ化）。
2. **環境適応**:
   - `HERDR_ENV=1` かつ `herdr` コマンドが存在する場合: Herdrのマルチペイン分割（`herdr pane split`）とテキスト送信を実行。
   - それ以外（通常ターミナル、tmux、SSH環境等）: カレントペイン内で指定エージェントを直接フォールバック起動。
3. **配布インターフェース**:
   - リポジトリ構造を `gh extension` 準拠（ルートに実行可能ファイル配置、またはリリースバイナリ配布）にし、`gh extension install kuwa72/herdr-gh-flow` で `gh flow`（または `gh hgf`）として即座に利用可能にする。

### 提言2: UXは「1ストローク選定 ＆ Human-in-the-loop レビュー」を基本とすべき
1. **Issue選定時のエージェント直結キーバインド**:
   - Issueを選んでから「どのエージェントで起動しますか？」とプロンプトを出すとテンポが阻害される。
   - `fzf` の `--expect` 機能（Go/TUI化後はキーリスナー）を活用し、`[Enter]` (標準agy) / `[Ctrl-D]` (devin) / `[Ctrl-O]` (opencode) 等で**1回のキー入力でエージェント指定まで完了**させる。
2. **安全とペアプロ感を担保するプロンプト事前展開**:
   - エージェントペインを起動した直後、いきなり自動実行（Enter送信）するのではなく、エージェントの入力欄に**プロンプト文字列が入力された待機状態**にする。
   - 開発者がプロンプトを一瞥し、補足があれば追記して `[Enter]` を押すUXにより、エージェントの暴走や見当違いな方向への進行をゼロコストで防止できる。
