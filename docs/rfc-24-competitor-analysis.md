## 1. 思想と前提の再定義

本調査および `lead-cli`（`lead`）の設計にあたり、以下の前提・カルチャーを中核に据える。

1. **「GitHub Issue基点で開発する」カルチャーの啓蒙**:
   - 世間一般の企業ではJira/Backlog等の外部チケット管理やスプレッドシート運用も依然多いが、`lead` では**「コードとIssueとPRが不可分に結合したGitHubネイティブな開発フロー」を推進・標準化する**ことを基本思想とする（他チケット管理はAPI/MCP連携レイヤで吸収可能と位置づける）。
2. **AIネイティブ時代における Issue / PR 粒度の再定義**:
   - 人間が手書きしていた時代は「小さければ小さいほど良い（数十行単位）」が鉄則だった。
   - しかしエージェント駆動開発では、小さすぎるタスクはコンテキスト設定のオーバーヘッドが勝り効果が薄い。
   - 逆に**「テストコード込みで数ファイル〜千数百行規模のまとまり」こそが、エージェントが前後の整合性を保って自律走行するのに最も費用対効果が高い単位**である。
   - したがって、Issueの受入条件もこの「エージェントが1回で走りきれる粒度」を前提に設計・起票支援されるべきである。
3. **認証と依存関係の割り切り**:
   - 外部アクセストークン（PAT等）の個別管理は不要とし、インストール済みの `gh` コマンドが返す出力・セッションをそのまま活用する。

## 2. 競合・類似ツールの空白地帯（The Gap）

既存のエコシステムは「タスク閲覧」と「エージェント作業」に分断されている。

```
[GitHub CLI / gh extension]           [lead (オーケストレーター)]          [AI Coding CLI / エージェント周辺]
┌─────────────────────────┐           ┌──────────────────────┐          ┌───────────────────────┐
│ gh-dash / gh-i / poi    │           │ lead-cli        │          │ Claude Code / agy /   │
│ ・Issue / PR 一覧・閲覧 │           │ ・Issue選択〜分解    │          │ Aider / Devin         │
│ ・単発のGit/ブランチ操作│ ── 欠落 ──>│ ・TDDプロンプト生成  │ ── 欠落 ─>│ ・ファイル編集        │
│ ※エージェント連携なし   │           │ ・マルチペイン配置   │          │ ・対話・コード生成    │
│                         │           │ ・CI追従・Auto-merge │          │ ※開発フロー規約なし  │
│                         │           │                      │          │ ※単一端末を占有      │
└─────────────────────────┘           └──────────────────────┘          └───────────────────────┘
```

- **`gh extension`（`gh-dash`, `gh-i`, `gh-poi` 等）**:
  - `gh extension install <repo>` で即座に導入でき、GitHub認証を透過利用できる優れた配布モデルを持つ。
  - しかし「Issueをプレビューした後に、どのエージェントにどういうTDD規約で着手させるか」という実行パイプラインが欠落している。
- **AIコーディングCLI（Claude Code, Aider, Devin, Antigravity CLI）**:
  - 端末内で優れたコード編集能力を持つが、「ブランチ作成」「失敗するテストの作成（Red）の確認」「CI完了待ち」「マージ判定」という開発サイクル（Outer Loop）はすべて人間の手動操作に委ねられている。

## 3. オープンソース / エージェント周辺ツール（Awesome Claude Code等）の競合・類似調査

コミュニティ内で登場しているClaude CodeやAI CLIの周辺ツール群との比較・重複検証を実施。

### 3.1 オーケストレーター系（Claude Squad, Claude Code Flow, TSK等）
- **Claude Squad**: 複数ワークスペースで複数のClaude Codeを同時実行・管理するターミナルアプリ。
  - *leadとの違い*: 端末・プロセスの並列管理が主目的であり、GitHub Issueの取得・ブランチ作成・CI監視〜Auto-mergeというGit/GitHubフローにはタッチしない。
- **Claude Code Flow**: 再帰的にコードを書いてテスト・最適化する自律サイクル層。
  - *leadとの違い*: エージェント内部のループ（自律コーディング）の強化であり、Issue起点で開発者が司令塔として手綱を握る体験ではない。
- **TSK (Task Manager & Sandbox)**: DockerサンドボックスでAIエージェントにタスク委譲するRustツール。
  - *leadとの違い*: 安全なコンテナ隔離実行を主眼としており、ローカル直結のTDDやHerdr等の端末マルチプレクサ連携とは方向性が異なる。

### 3.2 ガードレール・フック系（TDD Guard, Go quality hooks等）
- **TDD Guard**: ファイル操作を監視し、テスト先行原則（TDD）に違反する変更をブロックするClaude Code用フック。
  - *示唆*: TDD遵守の重要性は広く認識されている。`lead` ではフックによる事後ブロックではなく、**「Issue本文＋受入条件からRed→Greenフローを明記した初期プロンプト」を起動時に動的注入する**ことで事前ガードレールを実現している。

### 3.3 スラッシュコマンド系（`/analyze-issue`, `/create-pr`, `/tdd`）
- 特定エージェント（Claude Code）専用の個別コマンド群。
  - *leadとの違い*: Claude Code単体で閉じており、`agy`（Antigravity CLI）や `devin`、`opencode` 等のマルチエージェントを横断できない。また、端末を占有するため開発者が横でGit diffや手動検証を並行操作できない。

## 4. Herdr ネイティブプラグインの先行事例調査

Herdr公式プラグインエコシステムにおいて、GitHubやIssue/タスクを扱うプラグインが先行して登場している。これらとの機能比較と棲み分けを分析した。

### 4.1 `ogulcancelik/herdr-plugin-github-start`（最も直接的な先行ツール）
- **概要**:
  - GitHub Issue / PR / Discussion のURLや番号を入力すると、名前付きセッション（Pi, Codex, Claude Code）を検索・復帰・新規起動する Herdr プラグイン（`herdr plugin install ogulcancelik/herdr-plugin-github-start`）。
- **共通点**:
  - GitHub Issue を起点に Herdr 内でエージェントを起動するコンセプト。
- **決定的な違いと `lead` の優位性**:
  1. **ワークフロー自動化の有無**:
     - `github-start` は「エージェントの起動（`agent start`）」で責務が終了する。作業ブランチの作成（`git checkout -b`）、受入条件の動的抽出、PR作成、CI追従・Auto-merge（`ci-wait`）といった**Git/GitHubの開発ライフサイクルは一切面倒を見ない**。
  2. **TDD規約プロンプトの強制力**:
     - `github-start` は単にURLを渡すか「see {url}, lets discuss the problem」程度の固定プロンプトを送るのみ。`lead` のような「Red（テスト失敗確認）→ Green → run-tests」を義務付ける動的プロンプト注入機能はない。
  3. **提供形態の柔軟性（Herdr非依存性）**:
     - `github-start` は Herdr プラグイン専用。Herdr がない通常の端末やSSH環境では一切動作しない。一方 `lead` は単体CLI/gh extensionとしてもフォールバック動作する。

### 4.2 `osolmaz/ghzinga`（Rust製 TUI Issue/PR ビューア & Herdrプラグイン）
- **概要**:
  - Rust製の高速・クリック可能な TUI GitHub Issue/PR ビューア（`gzg`）。
  - Herdrプラグイン版（`osolmaz/ghzinga/plugins/herdr`）も備え、Herdr内でGitHubのURLをクリックした際に右ペインにビューアを自動オープン/再利用する。
- **leadとの関係・示唆**:
  - `ghzinga` は「Issue/PRの閲覧・コメント・手動マージ（UI表示）」に特化している。エージェントを起動してコードを書かせる機能はない。
  - **示唆**: `lead` のIssue選択プレビューや、右ペインでの情報閲覧において、将来的に `ghzinga` のような高度なリソースビューアと連携（または思想を吸収）できるポテンシャルがある。

### 4.3 `miiraheart/herdr-beads`（タスクボード/Kanban Herdrプラグイン）
- **概要**:
  - ローカルタスク管理ツール `bd` (beads) を Herdr のサイドバー（ドック）やフローティングPopupとして埋め込み、List/Table/Kanbanでタスクを管理・更新するプラグイン。
- **leadとの関係・示唆**:
  - GitHub Issue ではなく `bd` のローカルDBを扱うタスクボード。
  - **示唆**: 「エージェントが作業する横で、人間がタスク進捗やステータス（Kanban）を常時サイドバーで確認する」というUXモデルにおいて、`lead` の今後の画面分割設計（左：司令塔・進捗 / 右：エージェント作業）に強い示唆を与える。

## 5. 開発者視点のワークフロー摩擦とマトリクス比較

| 開発ステップ | 従来の手動フリクション | 既存ツールの限界 | `lead` による解決 |
| :--- | :--- | :--- | :--- |
| **1. Issue確認・選択** | ブラウザや `gh issue list` で探して仕様・URLをコピー | `gh-dash`, `gh-i`: 閲覧は快適だが次の作業に繋がらない | `fzf` プレビュー＋1キーでブランチ作成とプロンプトへ直結 |
| **2. Issue粒度調整** | チケットが大福帳または曖昧でエージェントが暴走 | エージェント単体: 曖昧な指示から適当にコードを書き始める | 「千行規模・テスト込みで走れる粒度」へのAI起票・分解支援 |
| **3. TDDプロンプト注入** | 「テストを先に書け」「失敗を確認しろ」と毎回指示 | エージェント単体: 規約を忘れて実装から着手しがち | Issue本文＋受入条件＋厳格TDDルールを動的合成して注入 |
| **4. 実装・見守り・介入** | 単一端末だとログで画面が埋まり、Git diffが見られない | Claude Code / Aider / Squad: 単一端末または別ウィンドウ | 左右分割：左でGit・ログ監視、右でエージェント稼働 |
| **5. CI待機〜Auto-merge** | CI開始の未登録ラグ待ち、ブラウザ連打やポーリング | `gh pr checks --watch`: 直後のラグで未検出終了する | **`ci-wait`**: ラグ・再生成・コンフリクト判定を吸収して安全マージ |

### 詳細マトリクス

| 評価軸 | gh-dash / gh-i | Claude Squad / Flow | Claude Code / Aider | Devin / SWE系 | **lead-cli (lead)** |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **Issue選定・プレビュー** | ◎ (TUI一覧) | ✕ | ✕ (手動コピペ) | ◯ (Web/API) | **◎ (fzf + 本文プレビュー)** |
| **ブランチ自動作成** | ✕ (手動) | ✕ | ✕ (手動) | ◎ (自動) | **◎ (Issue slug自動作成)** |
| **TDD規約の強制注入** | ✕ | △ (内部ループ) | ✕ (プロンプト手動) | △ (指示頼み) | **◎ (Red→Green動的注入)** |
| **マルチエージェント切替** | — | ✕ (Claude専用) | ✕ (自社専用) | △ (限定モデル) | **◎ (agy, claude, devin等 1キー)** |
| **画面分割・情報分離** | ✕ | ◯ (ワークスペース) | ✕ (端末占有) | ✕ (Web別タブ) | **◎ (マルチペインで人間と並行監視)** |
| **人間の即時介入 (ペアプロ)**| — | △ | ◯ (対話) | ✕ (放置型) | **◎ (隣接シェルから即介入・微修正)** |
| **CI監視〜Auto-merge** | ✕ (手動監視) | ✕ | ✕ (人間が監視) | ◯ (PRまで) | **◎ (`ci-wait` による完全自動化)** |

## 6. UX設計：マルチペインで「ユーザーは何をして、何が起きるのか？」

単に画面を割るのではなく、**「人間が手綱を握り、エージェントが自律駆動する」**ための明確な役割分担を定義する。

### 6.1 画面レイアウト（左右分割）
```
┌──────────────────────────────────────┬──────────────────────────────────────┐
│  左ペイン: [人間の司令塔・検証環境]      │  右ペイン: [エージェント作業場]       │
│                                      │                                      │
│  - lead 実行・Issue選択・ブランチ作成   │  - agy / claude 等のエージェント起動   │
│  - git status / git diff のリアルタイム確認 │  - コード自動編集・ツール実行ログの流出 │
│  - テスト・ビルドの手動検証コマンド     │  - 人間への承認要求（Blocked状態）の提示│
│  - CI進行監視 (`bin/ci-wait`)         │                                      │
│  - ブラウザ起動・関連リンク確認         │                                      │
└──────────────────────────────────────┴──────────────────────────────────────┘
```

### 6.2 具体的なユーザー操作フロー
1. **着手（左ペイン）**:
   - ユーザーが `lead` を実行。`fzf` でIssueを一覧・プレビューし、キー入力（`[Enter]` 等）でIssueとエージェントを選択。
   - `lead` が作業ブランチを自動作成し、右ペインを生成してエージェント起動コマンドと動的生成プロンプトを展開。
2. **レビュー＆発火（右ペインへ視線移動）**:
   - プロンプトはいきなり自動送信されず、**入力欄に展開された待機状態**でフォーカスされる。
   - ユーザーはプロンプト（受入条件など）を一瞥し、必要なら微修正して `[Enter]` で開始する（**Human-in-the-loop**）。
3. **作業中（左ペインで監視・見守り）**:
   - 右ペインでエージェントが実行ログを流しながら自律的にテスト・実装を進める。
   - ユーザーは左ペインで `git status` や `git diff` を叩き、変なファイル改変がないか横目で監視。
   - 必要に応じて左ペインから手動テストを実行したり、ブラウザでPR/Issueリンクを開く。
4. **完了・マージ（左ペインで自動追従）**:
   - エージェントがPRを作成。
   - 左ペインで `bin/ci-wait <PR番号>` がチェック未登録ラグを吸収しながらCIを監視し、成功後にマージを実行・IssueをCloseする。

### 6.3 ターミナルマルチプレクサ基盤としての落とし所
- 仮想ターミナル（PTY制御・ANSIパース）やマルチプラットフォーム対応をゼロから自作するのは、WarpやCursorの再開発になり工数上泥沼化する。
- したがって、**「Herdr（`herdr`）が存在する場合はHerdr API（`pane split`, `pane send-text`）をフル活用し、存在しない環境（通常ターミナル/tmux）ではインラインまたは警告付きでフォールバック動作する」** という落とし所を採用する。

## 7. `gh extension` の仕様と位置づけ

### 7.1 `gh extension` とは
- GitHub CLI（`gh`）の公式拡張プラグイン機構。
- `gh-<name>` という形式のリポジトリを用意することで、ユーザーは `gh extension install <repo>` の1コマンドで拡張をインストールできる。
- インストール後は `gh <name>`（例: `gh flow` や `gh lead`）として、`gh` 本体のサブコマンドのように透過的に実行できる。

### 7.2 採用理由とメリット
1. **配布・インストールの極小化**:
   - OSごとのパッケージマネージャー登録が不要。GitHubリポジトリさえあれば即座に全ユーザーへ配布・アップデート可能。
2. **GitHub認証の透過性**:
   - ユーザーがすでに `gh auth login` していれば、追加のAPIトークン設定なしに `gh issue` や `gh pr` APIを利用可能。
3. **導入の敷居を下げる**:
   - `lead` を単独のスクリプトとしてクローンさせるよりも、「`gh` の拡張機能」として案内する方がGitHubユーザーにとって心理的抵抗が少ない。

## 8. 親課題 #16 へのインプット提言

1. **提供形態の決定**:
   - **ハイブリッド型（単体CLI `bin/lead` + `gh extension` エントリポイント）**:
     - リポジトリのルートに `gh` 拡張用エントリポイントを配置し、`gh extension install kuwa72/lead-cli` で `gh flow` として利用可能にする。
     - 内部では `HERDR_ENV=1` を検知してマルチペイン連携を行い、Herdrがない場合はインラインフォールバックする。
2. **Issue粒度・プロンプト起票支援の設計（#25 への接続）**:
   - エージェントが1回で走りきれる「千行規模・テスト込み」の粒度でIssueを起票・分割するためのテンプレートまたはAI支援コマンドの仕様策定を推奨。
3. **UXモデルの決定**:
   - 「左ペイン（人間主導：Git・監視・検証・リンク展開）」＋「右ペイン（エージェント：作業・対話・発火前レビュー）」の左右2分割モデルを標準UXとして承認することを推奨。
