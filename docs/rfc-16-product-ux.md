## 1. 背景と目的

`herdr-gh-flow`（`hgf`）は、GitHub Issue を起点に TDD・PR 作成・CI 追従・マージまでを最小手数で回すための AI オーケストレーターである。先行する #24 と #22 で、競合空白地帯、技術基盤、および提供形態の候補が調査された。

本 RFC では、これらの調査結果を統合し、以下を正式に決定・承認する。

1. **提供形態の確定**: 単体 CLI バイナリ `hgf` と Herdr 環境自動検出を組み合わせた形態
2. **基本UXモデルの確定**: 1 ストローク選定（組み込み TUI）＋ Human-in-the-loop レビュー（プロンプト事前展開待機）＋ 左右マルチペイン（左：人間司令塔／右：エージェント作業場）
3. **後続タスク（#25, #26）への基本要件の承認**

---

## 2. 前提と制約

- GitHub 認証は `gh` CLI の既存セッションを透過利用する。個別 PAT 管理は不要。
- ターミナルマルチプレクサの PTY 制御やクロスプラットフォーム TUI をゼロから自作しない。Herdr がある場合はその API を使い、ない場合はインラインフォールバックする。
- AI ネイティブな開発では、人間時代の極小 PR ではなく「テスト込みで数ファイル〜千行規模」の Issue を 1 回で走りきれる単位とする。

---

## 3. 提供形態の決定

### 3.1 単体 CLI バイナリ `hgf`

- 実装言語は Go とし、単一の静的バイナリ `hgf` を提供する。
- 外部コマンドへの依存は `gh` のみ必須とし、`fzf` などは組み込み TUI で代替する。
- GitHub Releases、Homebrew、インストールスクリプト等で直接入手可能にする（詳細は #26）。

### 3.2 Herdr 環境自動検出

- 起動時に `HERDR_ENV=1` および `herdr` コマンドの有無を判定する。
- Herdr 検知時: `herdr pane split` による右ペイン生成と `herdr pane send-text` によるプロンプト展開を行う。
- Herdr 非検知時: 現在の端末に直接エージェント起動コマンドを表示し、ユーザーが [Enter] で発火するインラインフォールバックを提供する。

### 3.3 配布方式の原則（#26 への前提）

| 配布経路 | 提供物 | 備考 |
| :--- | :--- | :--- |
| GitHub Releases | `hgf_<os>_<arch>` | goreleaser 等でクロスコンパイル |
| Homebrew | `hgf` Formula | 必要に応じて別途検討 |
| インストールスクリプト | `install.sh` 等 | 必要に応じて別途検討 |
| シェル補完 | `hgf completion` | 詳細は #26 |

## 4. 基本UXモデルの決定

### 4.1 1 ストローク選定（組み込み TUI）

- 外部 `fzf` への依存を排除し、Go 製 `koki-develop/go-fzf`（bubbletea ベース）を組み込む。
- `hgf` 起動時に `gh issue list` を取得し、あいまい検索＋本文プレビュー付きのリストを表示する。
- 1 つの選択画面で Issue とエージェントを同時に決定する。
- 主要キー（暫定）:
  - `[Enter]` → デフォルトエージェント `agy`
  - `[Ctrl-D]` → `devin`
  - `[Ctrl-O]` → `opencode`
  - `[Ctrl-C]` / `[Esc]` → 中止

### 4.2 Human-in-the-loop レビュー（プロンプト事前展開待機）

- エージェントにプロンプトを勝手に送信しない。
- 右ペイン（または現在端末）の入力欄に、Issue 本文・受入条件・TDD ルールを含むプロンプトを事前展開し、ユーザーが確認・微修正してから [Enter] を押して開始する。
- これにより、エージェント暴走やコンテキスト漏れを未然に防ぐ。

### 4.3 左右マルチペイン

| 領域 | 担当 | 操作 |
| :--- | :--- | :--- |
| 左ペイン | 人間の司令塔 | `hgf` 起動、ブランチ確認、`git status` / `git diff` 監視、手動テスト、`bin/ci-wait` 実行 |
| 右ペイン | エージェント作業場 | エージェント起動、コード編集、テスト実行、PR 作成要求 |

- Herdr 検知時は `herdr pane split --direction right --ratio 0.5` で生成する。
- Herdr 非検知時は単一端末で順次操作するが、ユーザーが `tmux` / `screen` 等を併用可能にする。

### 4.4 ユーザー操作フロー

1. **着手（左ペイン）**: `hgf` を起動し、組み込み TUI で Issue とエージェントを 1 ストロークで選定する。
2. **ブランチ作成**: `issue/<number>-<slug>` を自動生成し、切り替える。
3. **レビュー＆発火（右ペイン）**: プロンプトが入力欄に展開され、ユーザーが確認して [Enter] でエージェント開始。
4. **作業中（左ペインで監視）**: `git status` / `git diff` / 手動テストで改変を横目で確認する。
5. **完了・マージ**: エージェントが PR を作成した後、`bin/ci-wait` で CI 完了を追従し、承認次第マージ・Issue close する。

## 5. 後続タスクへの基本要件（#25, #26）

### 5.1 #25 ワークフロー柔軟性の設計への要件

- Issue と PR の対応関係を明確化する。基本は 1 Issue = 1 ブランチ = 1 PR とする。
- 調査・実験用途の Research モード、複数 PR への分割、中断・再開、作業状態の可視化を検討する。
- `git worktree` による並行作業をオプションでサポートする候補とする（Issue #3 も参照）。
- Issue 起票・分解支援のため、エージェント向け受入条件テンプレートを検討する。

### 5.2 #26 配布方式・インストーラー設計への要件

- Go 単一バイナリとしてビルドし、GitHub Releases への自動アップロードを基本とする。
- Homebrew Formula、インストールスクリプト、シェル補完の提供有無を検討する。
- バイナリは `HERDR_ENV` 非依存で動作し、Herdr がなくても最低限の機能を提供する。
